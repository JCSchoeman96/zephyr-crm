## Merge blockers. Fix in this order.

### P0-01. Remove the two-argument `accept_quote` handoff bypass

Evidence: **Confirmed.**
Files: `supabase/migrations/20260826205229_v140_sales_fulfilment_tracer_bullet.sql:276-308,563-567`; `docs/FULFILMENT_ARCHITECTURE.md:93-107`.

The authenticated two-argument overload locks a sent Quote, changes it to
`accepted`, and appends a Quote-only Activity. It does not convert the Lead,
create the Client, create the FulfilmentCase, create the planning Task, or write
the canonical cross-domain Activity. The migration explicitly grants this
overload to `authenticated`. The four-argument overload above it is the actual
atomic Sales-to-Fulfilment handoff.

Impact: an authenticated caller can leave an accepted Quote without the
required Fulfilment lineage. A later four-argument retry can encounter an
already-accepted Quote without a case and cannot repair the incomplete state.
This violates the v1.4 acceptance invariant and weakens the frozen Quote
contract.

Patch:

1. Make the two-argument compatibility path delegate to the canonical
   four-argument implementation with an explicitly documented internal source,
   or revoke its authenticated grant and migrate every still-valid legacy
   caller to the canonical signature.
2. Keep idempotent retries returning a complete existing handoff, never merely
   an accepted Quote.
3. Add a direct SQL boundary test for every exposed overload: first call,
   stale-lock retry, idempotent retry, and rollback when case/task creation
   fails. Assert Client, FulfilmentCase, planning Task, and Activity lineage.
4. Update the compatibility comment and P7 regression coverage to describe the
   chosen public surface.

### P0-02. Close the generic Quote terminal-state and legacy decline bypass

Evidence: **Confirmed.**
Files: `supabase/migrations/20260821220000_quote_domain_hardening.sql:528-570,721-746`; `supabase/migrations/20260826205229_v140_sales_fulfilment_tracer_bullet.sql:552-573`.

`transition_quote_status` remains executable by `authenticated` and accepts
terminal states including `accepted` and `declined`. It updates only the Quote
and appends a Quote Activity. The two-argument `decline_quote` wrapper calls
this generic function, so an authenticated caller can decline a sent Quote
without applying the canonical Lead-loss closure, active lost-reason rules,
lost notes rules, task closure, and Lead Activity.

Impact: the public RPC surface still exposes a pre-v1.4 state mutation that can
produce Quote/Lead disagreement. The same generic function also provides an
alternate acceptance path around the canonical handoff.

Patch:

1. Decide whether compatibility is required. If not, revoke authenticated
   execute on `transition_quote_status` and the two-argument decline/accept
   wrappers, retaining only private or trusted migration helpers.
2. If compatibility is required, make each public compatibility wrapper
   delegate to the canonical evidence-bearing action with complete semantics;
   do not synthesize a lost reason that was not supplied by the caller.
3. Keep public terminal transitions allow-listed at the canonical boundary and
   remove any authenticated generic transition that can reach `accepted`.
4. Add direct authenticated RPC tests proving that every accepted/declined path
   either performs the complete handoff/closure or is rejected, including stale
   locks and invalid/missing lost evidence.

### P0-03. Restore `reopen_lead` AAL2 and security-audit enforcement

Evidence: **Confirmed.** Also reported by the formal security scan.
Files: `supabase/migrations/20260826200602_v140_fulfilment_persistence_foundation.sql:656-697`; prior authority in `supabase/migrations/20260822160000_v131_authority_reconciliation.sql:577-595`; route pre-check in `src/routes/leads/[id]/+page.server.ts`.

The v1.3.2 implementation required `private.require_current_session_aal2()`
and wrote `private.record_security_audit(...)`. The v1.4 persistence
migration replaces the function and retains only the Owner/Admin role and
reason checks. Runtime inspection confirmed `reopen_lead(uuid,bigint,text)` is
executable by `authenticated`, while the current function body has no AAL2
check or security-audit call.

Impact: a privileged correction path lost the step-up-authentication and
security-audit guarantees established by the prior authority. The SvelteKit
role check is not a substitute for the database boundary.

Patch:

1. Restore the AAL2 assertion and security-audit record in the final function
   definition, preserving the current lock and reason validation.
2. Add an AAL1 rejection test that proves no Lead or Activity mutation occurs,
   an AAL2 success test, and an audit-row assertion.
3. Add migration-order coverage so later `create or replace function` changes
   cannot silently remove mandatory security calls.
4. Mirror the AAL2 requirement in the route UX with a safe step-up/re-auth
   message; retain the database check as the authoritative enforcement.

### P0-04. Prevent forged qualification evidence on raw Lead INSERT

Evidence: **Confirmed.** Also reported by the formal security scan and locally
reproduced in a rollback-only transaction.
Files: `supabase/migrations/20260826200602_v140_fulfilment_persistence_foundation.sql:7-23,316-346`; `supabase/migrations/20260823100000_rh02_trusted_boundaries.sql:17-40`; `supabase/migrations/20260821194640_database_identity_permissions_rls.sql:610,687-694`.

The protected UPDATE trigger covers `qualification_notes`,
`qualification_started_at`, and `qualified_at`, but the authenticated INSERT
trigger does not reject those fields. Authenticated CRM roles also retain Lead
INSERT and INSERT policy access. A local transaction using an active Owner
identity inserted a new `NEW` Lead with forged notes and both qualification
timestamps; the transaction was rolled back after returning:

```text
NEW|forged qualification evidence|true|true
```

Impact: a caller can create a Lead carrying qualification evidence that did not
come from `start_lead_qualification` or `ready_lead_for_quote`. Even though the
pipeline stage remains `NEW`, downstream reporting or recovery logic can treat
the timestamps/notes as trusted facts.

Patch:

1. Extend the trusted initial-state guard to reject non-null qualification
   fields for ordinary authenticated INSERTs, or move all such creation to a
   trusted ingestion boundary with an explicit, documented exception.
2. Add a database security contract for forged qualification notes, start time,
   qualified time, and invalid timestamp combinations.
3. Preserve tests proving the two dedicated qualification actions can write
   the fields, while raw authenticated INSERT cannot.
4. Review any other system/provenance fields added after the original INSERT
   guard and make the guard/table authority lists cumulative.

## Policy decisions required before security behavior can be finalized

### P1-01. Define the public `convert_lead` policy

Evidence: **Decision required.**
Relevant code: the public `convert_lead` RPC and its grants; the call from
`accept_quote` in `supabase/migrations/20260826205229_v140_sales_fulfilment_tracer_bullet.sql:189-192`.

`accept_quote` correctly uses the existing idempotent conversion inside its
atomic handoff. Separately, the direct `convert_lead` path remains available to
Owner/Admin/Sales and does not require an accepted Quote. The older security
matrix says Sales may convert/win/lose Leads, while the v1.4 Fulfilment
authority describes Quote acceptance as the normal path and leaves conversion
as policy-dependent recovery.

Choose one authority outcome and align grants, tests, docs, and audit semantics:

- strict v1.4: restrict direct conversion to a trusted recovery/admin path;
- compatibility: retain Sales access but explicitly classify it as a recovery
  operation, with required reason/audit evidence and no ordinary DECISION→WON
  bypass.

Do not resolve this by silently removing a frozen P7 capability.

Resolution (2026-08-27): Compatibility is retained. The two-argument
`convert_lead` action remains restricted to Owner/Admin/Sales, is documented as
migration/recovery-only rather than a normal browser decision, and records a
dedicated security-audit event plus Activity source marker on each new
conversion. Frozen callers remain intact and the hardening contract covers the
policy boundary.

### P1-02. Define whether generic `transition_lead` is still a public workflow API

Evidence: **Decision required.**
File: `supabase/migrations/20260826200602_v140_fulfilment_persistence_foundation.sql:576-654`.

The generic RPC allows NEW→QUALIFICATION, QUALIFICATION→PROPOSAL,
PROPOSAL→DECISION, and DECISION→PROPOSAL/LOST. It records timestamps but does
not enforce the dedicated qualification evidence checks used by
`start_lead_qualification` and `ready_lead_for_quote`. Under a strict
interpretation it is another route around the evidence-bearing actions; under
the compatibility authority it is a frozen endpoint.

Choose whether to retire/restrict it or explicitly document it as a compatible
workflow path. Add negative tests for missing contact/enquiry evidence if it
remains public, and update the state-machine/security authority consistently.

Resolution (2026-08-27): Compatibility is retained for non-terminal workflow
stages and `LOST`. The final database function rejects `WON` and requires
usable contact plus meaningful enquiry evidence for `QUALIFICATION → PROPOSAL`;
the dedicated qualification actions remain the preferred browser contract.

## Important correctness and pilot-readiness follow-ups

### P1-03. Remove global relation caps from Fulfilment queues

Evidence: **Confirmed.**
Files: `src/lib/server/fulfilment.ts:16-23,179-216,271-363`.

The queue loads up to 100 cases but applies one global cap of 500 steps, 250
payment milestones, and 500 tasks across all selected cases. A busy case can
consume the cap and cause other cases to appear to have no work. Detail loading
also caps steps/payments/tasks/activities without a truncation indicator.

Patch with per-case queries, a bounded server-side aggregation, or explicit
pagination/continuation. Return enough metadata to distinguish “empty” from
“not loaded”. Add fixtures exceeding each cap and assert every visible case is
classified from complete data.

### P1-04. Remove the global Sales quote cap or make revision loading complete

Evidence: **Confirmed.**
File: `src/lib/server/sales-queue.ts:14-69`.

The Sales queue loads 50 Leads, then one global 250-row Quote set for proposal
and decision queues. A Lead with many revisions can have its current actionable
Quote omitted even though the Lead row is present.

Patch with per-Lead latest-quote selection, a database view/RPC, or pagination
that preserves the latest actionable revision for every loaded Lead. Test more
than 250 revisions distributed across multiple Leads.

### P1-05. Make `datetime-local` scheduling timezone-safe

Evidence: **Confirmed.**
Files: `src/routes/fulfilment/[id]/+page.server.ts:37-43`; `src/routes/fulfilment/[id]/+page.svelte:34-44`; configured timezone in `src/lib/config/client-config.ts`.

The server converts a timezone-less `datetime-local` string with `new Date()`;
the detail view converts stored UTC with `toISOString().slice(0, 16)`. The UI
otherwise declares `Africa/Johannesburg` as the configured display timezone.
Browser timezone and configured business timezone can therefore disagree, and
editing a displayed schedule can shift it.

Patch with one shared IANA-aware conversion contract for display and form
round-trip, make the timezone visible near the input, and add tests around the
configured zone, UTC/CI zone, and DST-sensitive zones.

### P1-06. Align privileged-action UX with database AAL2 enforcement

Evidence: **Confirmed.**
File: `src/routes/fulfilment/[id]/+page.server.ts:56-75,181-240`.

The route pre-checks role for Owner/Admin actions, but the database enforces
AAL2 for sensitive payment correction and Fulfilment cancellation. An AAL1
request reaches the RPC and is returned through the generic raw error path.

Patch a typed error/status mapping for step-up-required responses and a clear
re-authentication path. Keep the DB AAL2 check and add route/browser tests for
AAL1, AAL2, viewer, and non-owner/admin callers.

### P1-07. Make Realtime claims match publication and subscription coverage

Evidence: **Confirmed.**
Files: `src/lib/realtime/RealtimeStatus.svelte:6-39`; `src/routes/fulfilment/+page.svelte:26-34`; `src/routes/fulfilment/[id]/+page.svelte:98-105`; local publication metadata.

The component supports only `leads`, `tasks`, and `quotes`. Fulfilment pages
subscribe only to `tasks` and `quotes`, while local publication is enabled only
for `quotes` and `tasks`; case, step, payment, and Activity changes do not
trigger the displayed “Live updates” status.

Either add the required publication/subscription coverage and test it, or
narrow the status copy and page contract to the tables that are genuinely live.
Avoid implying that all Fulfilment detail history is realtime when it is not.

### P2-05. Replace raw action-error exposure with stable error codes

Evidence: **Confirmed.**
Files: `src/lib/server/action-errors.ts:1-27` and affected route actions.

The current helper returns raw database messages to the browser and maps every
failure to HTTP 422. This leaks implementation wording and prevents reliable
client behavior for not-found, forbidden, conflict, validation, and step-up
cases.

Patch a small allow-listed mapping, for example: lock conflict → 409,
permission → 403, not-found → 404, validation → 422, with safe user text and
server-side diagnostic logging. Add tests for each SQLSTATE/action boundary and
ensure secrets or SQL details never reach the UI.

### P2-06. Remove the `as never` RPC escape hatch

### P2-07. Enforce complete Task lineage for Fulfilment work

Evidence: **Confirmed**.
File: `supabase/migrations/20260826200602_v140_fulfilment_persistence_foundation.sql:299-310,699-817`.

The Task trigger checks Quote lineage only when `new.quote_id` is non-null, and
the private task implementation accepts a null Quote for a Fulfilment case.
This may be intentional for non-commercial follow-ups, but it allows a case

reflect it in the generated types/actions, and test allowed and rejected task
types explicitly.

### P2-08. Make detail truncation explicit

Evidence: **Confirmed**.

Detail views cap Activities at 100 and other relations at fixed limits without

## Migration, release, and product consistency follow-ups

Evidence: **Confirmed**.
