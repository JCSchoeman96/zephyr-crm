## Scope and test conditions

The merged v1.5.0 workflow was exercised in an isolated worktree using a
fresh local Supabase reset, the local Wrangler preview, a deterministic local
SendPulse fixture, and disposable non-sensitive browser data. No production
service or real recipient was used.

Viewports used:

- Desktop: 1280px-wide browser view.
- Mobile: 390x844.

The primary fixture was a service Product named `Roof Inspection Visit`, code
`OPS-ROOF-INSPECT-01`, initially priced at ZAR 1,850 per visit. The quote used
an additional custom coordination line, a negotiated catalogue price, 15% VAT,
and a disposable test customer.

## Commercial and document observations

The exercised Quote was:

- Custom line: 1 × ZAR 250.
- Catalogue line: 2.5 × negotiated ZAR 1,700 = ZAR 4,250.
- Subtotal: ZAR 4,500.
- VAT: 15% / ZAR 675.
- Total: ZAR 5,175.

The PDF contained the expected customer-visible facts and did not contain the
Product internal note. Its stored SHA-256 matched the downloaded bytes:

`2f50eff910ca5b1512f4e6f503bb1d2e8913fd42fbc7d587c0770d60e2b21fcb`

`pdfinfo` reported one A4 page and `pdfimages -list` reported no embedded
image. The rendered page was visually professional in spacing, hierarchy,
totals placement, and terms placement, but the following were visible:

- The seeded company identity points to `/favicon.svg`. The browser preview
  requested that path and received 404; the preview displayed a broken image
  icon. The document resolver accepts PNG/JPEG assets, so the actual PDF used
  the intended `ZC` monogram fallback rather than an approved logo asset.
- `quote_defaults.bank_details` is empty in the local seed. Therefore no bank
  details were rendered and their placement could not be accepted. This is a
  pilot configuration prerequisite rather than a claim that the layout is
  correct with real banking details.
- The long Product code wrapped as `OPS-ROOF-I` / `NSPECT-01`. It remains
  readable, but a less awkward code-column treatment would improve polish.

The local SendPulse fixture accepted the message and attachment and the
application recorded `delivery_status=submitted`, `attempt_count=1`, and a
provider message ID. A controlled real mailbox was not configured, so desktop
and mobile inbox rendering remains an external pilot check.

## Findings and patchlist

### HIGH

**OA-01 — Desktop Quote preview is too narrow.**  At the 1280px desktop
viewport, the editor’s right-hand preview is constrained to a narrow column.
Unit prices and amounts split digits across lines, and the terms paragraph
breaks into individual word fragments. This prevents a salesperson from
confidently reviewing the customer-facing preview at a normal desktop size,
although the generated PDF and the 390px mobile preview remain usable.

**OA-02 — Default branding does not produce an actual logo.**  The seeded
identity uses `/favicon.svg`, which is not served at that path and is not an
accepted PDF logo format. This causes a broken image in the builder and a
monogram fallback in the outgoing PDF. Before pilot use, configure an approved
PNG/JPEG logo or align the default asset path and preview fallback.

### MEDIUM

**OA-03 — The Ready for Quote shortcut hides the catalogue path.**  The
shortcut is useful for a quick custom quote, but its “Create a simple quote”
flow produced a Ready to send quote without showing the Product picker. A
product-led operator could reasonably assume the catalogue is unavailable or
skip reusable pricing. Clarify the distinction or surface the catalogue route
at this decision point.

**OA-04 — Banking details are not configured or operationally editable.**
The seeded defaults contain no bank details, and the Owner/Admin Operations
screen exposes diagnostics but no quote-default configuration. If customers
are expected to pay by bank transfer, approved business details must be
configured and a PDF recheck is required before pilot send.

### LOW

**OA-05 — Long Product codes have awkward PDF wrapping.**  The renderer fits
the code within the table, but the break point is visually untidy. This is a
document polish item, not a commercial or correctness failure.

## Workflow friction and positive observations

- Product creation and activation were understandable; the optional category
  field and “Uncategorised” list state were clear enough for a first run.
- The catalogue result card was fast to find and gave enough context to avoid
  selecting the wrong service.
- Negotiated pricing remained visible alongside catalogue price and source
  version, which made the commercial override understandable.
- Stale-source handling was explicit and safe: the operator could refresh or
  keep the quoted values, and the chosen decision appeared in history.
- The mobile quote builder is a long scroll, but it remains labelled, stacked,
  and free of horizontal overflow. The Fulfilment detail is similarly long but
  its overview and accepted-Quote lineage are easy to locate.
- Acceptance automatically cancelled the sent-quote follow-up and created a
  clear “Plan fulfilment” action, which made the handoff legible.

## Final recommendation

**PASS WITH PATCHLIST.** The complete Product → Enquiry → Quote → stale review
→ PDF → local provider submission → acceptance → Client → Fulfilment journey
works on the merged v1.5.0 baseline. No data-integrity, state-transition, or
local delivery blocker was found.

Resolve the desktop preview and real-logo issues before treating the workflow
as polished for a broad pilot. Configure approved bank details and perform a
controlled mailbox rendering check as pilot prerequisites. OA-03 and OA-05
are suitable for a compact v1.5.1 polish pass. No v1.6 work was started.

The disposable local database was reset after the review; final counts were
zero Products, Leads, Quotes, Outbound Messages, Clients, and Fulfilment
Cases.
